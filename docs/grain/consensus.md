# Консенсус и хранение GRAIN

GRAIN — детерминированный конечный автомат. Всё состояние сети — одно гранулированное Merkle-дерево.
Каждый блок — переход состояния. **Предмет консенсуса — не сам блок, а post-block состояние** (корень Merkle).

## Стадии блока

Каждый раунд проходит по цепочке (все стадии на алармах, без re-broadcast):

```
Ping → GetTx → ValidateBlock → BlockDiffValidate → BlockAccepted
```

1. **Ping** — лидер рассылает `PingREQ` (с `HeartBeatREQ` = prev_root_hash, new_epoch, node_leader).
   Нода отвечает `PingRSP` и **BLS-подписывает хэш hb** (`sig`). Лидер собирает ответы → **alive-сет**.
2. **GetTx** — лидер (`current_leader()`) собирает транзакции `GetTxREQ`/`GetTxRSP`.
3. **ValidateBlock** — лидер собирает блок (`do_start_block`) и рассылает `ValidateBlockREQ`.
4. **BlockDiffValidate** — валидаторы выполняют блок (`execute_block`), вычисляют дифф состояния
   и подписывают его BLS (`BlockDiffValidateRSP`).
5. **BlockAccepted** — лидер агрегирует подписи: `agg_diff_sig` + `node_diff_validators` (валидация диффа)
   и `agg_alive_sig` + `alive_validators` (подписанный alive-сет пинга) → `BlockAccepted2REQ`.

## Живость нод (alive-сет, а не счётчики)

- **Пинг объективен**: ответ подписан BLS, агрегат (`agg_alive_sig`) лежит в блоке и проверяется.
  Цензура пинга ограничена кворумом — выбросить можно только меньшинство.
- В `execute_block` для нод из alive-сета прошлого блока обновляется:
  - `activity._update_time` — источник для **физического удаления** (GC по TTL);
  - `node.last_update` — **кэш на bc_node**, чтобы не читать гранулу activity при фильтре vne.
- **Состав vne**: `enabled && node_active`, где
  ```
  node_active(n):
      если n.last_update == 0 → true          // sentinel «ещё не пинговал» (генезис/новая нода)
      иначе (block_ts - n.last_update) <= TTL // 60с
  ```
  `last_update == 0` — уникальный случай (как `ttl == 0` = вечный): генезис создаётся с `time0 = 0`,
  а старт нод у всех разный, поэтому `time(NULL)` в генезисе использовать нельзя.
- Ручной `node_enable`/`node_disable` — отдельный флаг `enabled` (опционально).

## Выбор лидера

- `current_leader() = committee[slot % size]`, где `slot = (now - lastBlockTime) / SLOT_MKS`
  (правый край слота — «мёртвая зона», лидера нет).
- `current_leader()` нужен **только для GetTx**. После него слот может уехать, но блок доделывается
  со «замороженным» лидером из `cli.node_leader`; по аларму `TIMER_BLOCK_EXPIRED` кэш сбрасывается.
- Комитет (`committee_vne`) — подмножество vne (строгий фильтр «уже пинговал» + stake, затем релакс-фолбэк).

## Кворумы

- Пинг: `is_PingRSP_m_quorum` — доля от полного включённого стейка.
- Дифф: `is_BlockDiffValidateRSP_m_quorum`.

## Структура хранения

- **Гранула** — атомарный фрагмент состояния. `path → value` в RocksDB; `path` — детерминированный
  путь от корня (это и есть ключ). Лист, к которому обратились, помечается dirty; после блока
  пересчитываются только изменённые листья и их родители вверх до корня.
- **Адресация контракта**: у контракта есть базовый адрес, все его данные лежат под этим префиксом
  (изоляция, нет коллизий).
- **granular_map** — дерево с ветвлением по base-62 (62/62²/62³…), для сотен миллионов записей.
  Нет MVCC, WAL, VACUUM, индексов — детерминированная структура, O(log N) обновление.
- **activity + TTL**: каждая гранула/нода/контракт имеет `bc_activity` (`_update_time` + `ttl`).
  Нет активности дольше TTL → GC физически удаляет. Явного удаления контрактом нет —
  правило «выставил TTL, нет активности → удалилось само». Удаление (тумбстоун) + пересоздание —
  через компакцию.

## Преимущества

- Обновление только изменённых листьев и их родителей — `O(log N)`, без пересборки всего дерева.
- Детерминизм: одни и те же транзакции → один и тот же root (предмет консенсуса).
- Нет MVCC/WAL/VACUUM/индексов — проще и дешевле эксплуатация.
- Подписанный alive-сет в блоке — объективная живость, а не «взгляд лидера».
- Чтения шардируются (любая нода), запись — через консенсус (CQRS).

## Нерешённое / на что смотреть

- Раскол `current_leader()` при расхождении `prev_root_hash`/`lastBlockTime` у нод (ловим трассой `MTJS_LEADER_TRACE`).
- Точная синхронизация слотов между нодами (зависит от wall-clock `now`).
- Сортировка дерева рассылки по `last_update` (отложена).

## Смена раунда и замок (спецификация, 2026-11)

Цель: убрать зависимость от кэша `cli.node_leader` и от «алармов, которые кто-то
сбросил», и сделать смену лидера детерминированной. Схема собрана из проверенных
элементов: лидер от слота (Solana-подобно), замок + 2/3-сертификат (Tendermint),
QC без переподписи (HotStuff).

### Инварианты

1. **Лидер детерминирован слотом**: `current_leader() = committee[slot % size]`.
   Один лидер на слот, полномочия за пределы слота не продлеваются.
2. **Раунд = слот.** Слот идёт по времени сам.
3. **Замок**: валидатор подписывает не более одного блока на высоту (`epoch`).
4. **Финал = 2/3 подписей** за хеш блока. После этого лидер не нужен: принятие
   собирает любой, у кого есть 2/3.

### Замок (`signed_block`)

- Хранится **вне дерева**: в `IDatabase` отдельным ключом (длина 5–27 символов,
  не пересекается с id ячеек). Не удаляется, перезаписывается при новой подписи.
- Значение: `pack(BlockInfo, sig)` — подписанный заголовок (`new_root_hash1`,
  `tx_hash`, `diffs_hash`, `att_data_hash`, `heart_beat`, `block_timestamp`) + подпись.
- В памяти — как `prev_block`; при старте подгружается из БД.
- **Валидность** (проверка перед подписью):
  ```
  lock.epoch == epoch_current() && lock.root != new_root   -> refuse (другой блок на той же высоте)
  lock.root == new_root                                    -> ok (идемпотентно)
  lock.epoch <  epoch_current()                            -> протух (блок применён)
  lock.epoch >  epoch_current()                            -> аномалия, лог
  ```

### Достройка новым лидером

Новый лидер — член комитета, поэтому **тело блока у него уже есть** (получал
`ValidateBlockREQ` в первом раунде). Нужны только подписи:

```
GetValidateBlockRSPREQ(root) -> GetValidateBlockRSPRSP(vector<ValidateBlockRSP>)
```

- >= 2/3 подписей за `root` — блок финален: собрать `BlockAccepted2REQ`
  (**детерминированный порядок валидаторов, сортировка по NODE_id**), применить,
  строить H+1.
- >= 2/3 голосов, но ни один root < 2/3 — **доказанный сплит**: замок снимается,
  новый блок на той же высоте.
- < 2/3 голосов вообще — **неизвестно**: стоять, замок не снимать (партиция).

### Ключевое правило

> Замок снимается только при ДОКАЗАТЕЛЬСТВЕ сплита (>= 2/3 голосов), а не по
> истечении времени. Timeout — повод начать сбор доказательств, не повод снять замок.

### Что убирается

- `cli.node_leader` как источник истины (максимум — подсказка).
- `resetBlockExpired` только в `GetTxREQ`: таймер становится детерминированным
  критерием голоса от слота.
- Проверка в `ValidateBlockREQ`: `src_node == current_leader()` вместо `cli.node_leader`.

## Реализация (шаги 3–5)

Сделано и проверено на 10-нодовом кластере (mp: 10 процессов):

- **Шаг 3** (`3c24e33`): `GetValidateBlockRSPREQ(epoch, base_root, root_hint)` /
  `GetValidateBlockRSPRSP(vector<ValidateBlockRSP>)`. Каждый узел хранит свой
  подписанный `ValidateBlockRSP` (2 эпохи, `my_signed_rsp`) и отдаёт его по
  запросу. Новый лидер собирает голоса, проверяет BLS, базу, эпоху и стейк
  комитета; сертификат — отсортированный по `NODE_id` вектор.
  - Запрос **по эпохе**, а не только по root: при расколе комитет подписывает
    разные руты, и для сплит-пруфа нужны все голоса.
  - Триггер: новый лидер на старте слота (`ALARM_Ping`) и `TIMER_BLOCK_EXPIRED`,
    если на текущей высоте есть наш замок у другого лидера.
- **Шаг 4** (`cab568e`): из сертификата собирается канонический
  `BlockAcceptedREQ` (агрегат + сортировка по `NODE_id`), запускается `BDV`;
  штатный путь `BA2 -> BlockDBStore` применяет блок.
  - `BlockDiffValidateREQ` больше не требует `cli.node_leader`: подлинность —
    2/3 aggregate-подпись за `blockInfo` + стейк-кворум. Если блок уже исполнен
    и подписан нами, подписывается hash BA без повторного применения диффов.
  - `BlockDBStore` принимается по сертификату, проверяются база, идемпотентность
    и локальный корень перед записью.
  - alive-сет для BA2 у достройщика восстанавливается перепингом `hb` блока
    (`cert_alive`): пустой `AggregateSignature` не сериализуется.
- **Шаг 5** (`b0e06fb`): `UnlockRoundREQ(epoch, base_root, proof)` —
  доказательство сплита (total > QUORUM, best <= QUORUM). Приёмник проверяет все
  подписи и снимает замок: дерево откатывается к корню из БД, пустой
  `...signed_block...` пишется в БД. Лидер заново стартует раунд и предлагает
  новый блок на той же высоте.

**Замок проверяется ДО `execute_block`** (`ValidateBlockREQ`): раньше отклонённый
блок успевал изменить дерево и `db_to_save_Z`, что при расколе давало мусор,
стопор высоты и разрастание памяти. Повтор того же блока отдаётся идемпотентно
из сохранённого RSP.

Тест-хуки (env, только для отладки):
- `MTJS_TEST_FREEZE_LEADER=1` + `MTJS_TEST_FREEZE_EPOCH=N` — заморозить автора
  блока перед рассылкой `BDV` (маркер `/tmp/regress/MTJS_FREEZE_ONCE`).
- `MTJS_TEST_FREEZE_AFTER_BROADCAST_US` — заморозить автора сразу после
  `ValidateBlockREQ` (частичная рассылка).
- `MTJS_TEST_SKIP_FIRST_EPOCH=N` + `MTJS_TEST_SKIP_FIRST_NODES=n0,n1,...` —
  инжект раскола: часть комитета «не получает» первый блок высоты.
- `MTJS_CERT_TRACE=1` — трасса сборки сертификата и BA/BA2.

Известные ограничения:
- `sync_in_progress` по-прежнему отбрасывает `GetTxREQ`/`BDV`/`BlockDBStore`:
  узел, завершивший синк ровно в окне `GetTx`, теряет раунд и может уйти в
  повторный синк (петля n7). Это отдельная задача — очередь/повтор входа в раунд
  после синка.
- alive-сет при достройке собирается с живых нод, а не из исходного пинга:
  набор может отличаться от исходного, но одинаков у всех (BA2 один).
