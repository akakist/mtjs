# CONSENSUS.md — консенсус субблоков (block-status)

> **Живой документ.** Меняется схема — меняем и его.
> Описывает целевую схему; код приводится к ней постепенно.

## Идея

Раунд блока собирается из **субблоков**. Субблок — это один оффер (пачка tx).
В раунде их может быть много → комитет исполняет их параллельно, а некомитет
параллельно применяет диффы. Отсюда высокая пропускная способность: узкое место —
не «один блок на 5 секунд», а агрегация подписей по пачке офферов.

Лидер — только агрегатор: он собирает подписи и рассылает статус.
Ничего, что влияет на безопасность, он не решает единолично — кворумы
проверяет каждая нода сама.

## Термины

- **Комитет** — детерминированный набор на раунд (`committee_vne[0]` — лидер).
- **Не-комитет** — остальные enabled-ноды.
- **Стейк** — `prevStakes` (стейки предыдущего блока). **Текущим стейком кворум не считается.**
- **Свёртка** — `proceed_merkle_on_transaction_pool_hashers` (листья → промежуточные узлы → корень).

## Сертификат = `BlockInfo`

`BlockInfo` — единственный документ, который подписывают и комитет, и некомитет.
В нём всё, что нужно для проверки блока:

| Поле | Источник |
|---|---|
| `prev_state_root` | `blockInfo->heart_beat->prev_root_hash_1` |
| `new_epoch` | `blockInfo->heart_beat->new_epoch` |
| `new_state_root` | `blockInfo->new_root_hash1` |
| `block_timestamp` | `blockInfo->heart_beat->block_timestamp` |
| `att_data_hash` | `blockInfo->att_data_hash` |
| `offer_hash` | `blockInfo->offer_hash` |

Хеш сертификата: `hash(BlockInfo)`. Он же — ключ мап `accepted` / `slash`.

## Структуры (цель)

```cpp
// серт одного варианта
struct BlockAcceptedREQ {
    REF_getter<BlockInfo> blockInfo;
    std::set<NODE_id>     node_validators;   // кто подписал
    blst_cpp::AggregateSignature agg_sig;    // агрегат ПОДПИСЕЙ этих нод
};

struct SubBlock {
    THASH_id offer_hash;
    THASH_id att_hash;

    // состояние ДО слэша: hash(BlockInfo) -> серт
    std::map<THASH_id, REF_getter<BlockAcceptedREQ>> accepted;

    // состояние ПОСЛЕ слэша: тот же BlockInfo, но с post-slash корнем
    std::map<THASH_id, REF_getter<BlockAcceptedREQ>> slash;

    // доказательства эквивокации (вторая подпись на ДРУГОЙ хеш)
    std::map<THASH_id, REF_getter<BlockAcceptedREQ>> double_signed_by_committe;
    std::map<THASH_id, std::pair<blst_cpp::AggregateSignature, std::set<NODE_id>>> double_signed_by_noncommitte;
};
```

`node_validators` — **сет** (детерминированный порядок в `update()`).
`accepted` одна, потому что комитет и некомитет подписывают **один и тот же**
`BlockInfo`; разделение на группы — только при расчёте кворума.

## Голос

`ValidateBlockRSP` несёт `blockInfo`, `sig`, `node_validator`, `round`, `subblock`
и поле **`slash`** (`false` — accept, `true` — slash).

Лидер кладёт голос по `hash(blockInfo)` в `accepted` или `slash` — по полю `slash`.
Все остальные это перепроверяют.

## Кворумы

Для варианта `h`:

```cpp
i128 stake_committee = 0, stake_all = 0;
for (n : accepted[h]->node_validators) {
    stake_all += prevStake(n);
    if (isMemberCommitte(n)) stake_committee += prevStake(n);
}
committee_quorum = stake_committee * 100 / full_stake_committe > QUORUM;  // 67%
all_quorum       = stake_all       * 100 / full_stake_all       > QUORUM;  // 67%
```

- **accept** валиден, когда оба кворума указывают на **один и тот же** `h`.
- **slash** валиден, когда набран `all_quorum` (67% всей сети); слэшнутые скипаются.
- Эквивокаторы (двойная подпись) **исключаются** из кворума.

## Фазы

```
1) КОМИТЕТ:  исполнил оффер -> свёртка -> корень A
             подпись ValidateBlockRSP(slash=false) -> accepted[A]

2) НЕКОМИТЕТ: получил att_data -> применил диффы -> свёртка -> корень A
             подпись ValidateBlockRSP(slash=false) -> accepted[A]

3) КВОРУМ A:  committee_quorum + all_quorum на один и тот же `h`

4) СЛЭШ (если есть double_signed):
             применить слэш (сжечь стейк) -> свёртка -> корень B
             все подписывают ValidateBlockRSP(slash=true) -> slash[B]

5) КВОРУМ B:  all_quorum

6) ФИНАЛ:    состояние уже свёрнуто -> записать merged + root_buf + prev_block
```

Если `slash` пуст (эквивокации не было) — финализируется `A` из `accepted`.

## Финиш раунда и пустой оффер

Последний субблок раунда помечается `SubBlock::last = true` — это «пустой»
субблок (без tx). После его кворума раунд закрывается: состояние флушится,
переходим к следующему блоку.

- Пустой оффер (`TxContainer` без tx) обязан иметь **уникальный хеш**, иначе все
  пустые офферы схлопнутся в кеше под одним ключом. Решение: включить
  `heart_beat` в `ValidateBlockREQ` (хеш зависит от hb раунда), либо частный
  случай `offer.container.size() == 0`.
- **Слэш — это не субблок.** Нода, увидев двойную подпись, в `ValidateBlockRSP`
  ставит `slash=true`, и голос уходит в `slash`-мапу. Отдельного
  `SUBBLOCK_SLASH` / `slashes` в оффере нет — оффер это только tx.

## Инварианты

1. Два `proceed_merkle` подряд на одном дереве несовместимы: первый сбрасывает
   `is_dirty`/обновляет `children_hashes`, второй становится no-op. Свёртка — один раз.
2. Диффы — **конечные листья**; промежуточные узлы рождает свёртка.
3. Финализация не пересчитывает состояние: берёт готовый `root_buf`.
4. `double_signed` заполняется только при подписи на **другой** хеш (дубль — игнор).
5. Поздний голос **не теряется**: он вставляется в `accepted` даже если субблок
   уже исполнен / кворум набран. Но в кворум засчитывается **только за победивший
   хеш** — остальное хранится для целостности картины, но не влияет на исход.
   Эквивокация (вторая подпись на другой хеш) фиксируется в `double_signed`.
6. Ключ `accepted`/`slash` = `hash(BlockInfo)`; `node_validators` — сет.
7. Кворум считает только `prevStakes`; текущее состояние на кворум не влияет.
8. Лидер не может подделать кворум: агрегат BLS проверяется по ключам из состояния.
9. Статус из старого раунда отбрасывается (`e->id != mf->round`).
10. **`finished` — законное решение лидера.** Он закрывает раунд: по этому флагу
    нода флушит состояние и переходит к следующему блоку. Лидер сам его и ставит.
11. Лидер складывает **подписи** в `agg_sig` (`AggregateSignature::add`);
    PK для проверки агрегируют сами верификаторы из состояния
    (`fast_aggregate_verify` суммирует `pks`, порядок не важен — сложение точек
    коммутативно). Кворум считают ноды; `finished` — решение лидера о закрытии.

## Слэши

Слэш — доказанное нарушение, за которое сжигается стейк нарушителя.
Доказательство всегда **детерминировано**: любая нода считает его одинаково
из данных статуса, поэтому «подставить» корректную ноду нельзя.
Позиция жёсткая намеренно: кривые блокстатусы начнут подставлять сразу,
и наказание должно быть мгновенным.

### Эквивокация ноды (двойная подпись)

Нода подписала **два разных** `hash(BlockInfo)` в одном субблоке.

- Доказательство: `double_signed_by_committe` / `double_signed_by_noncommitte` —
  вторая подпись + агрегат по ключам из состояния.
- Условие: подписант обязан быть и в `accepted` (первая подпись), иначе это не
  эквивокация, а битый статус (→ `corrupt`, виноват лидер).
- Ловится только **до** кворума. Поздние голоса эквивокацию не создают.

### Лидер за `corrupt` (кривой блокстатус)

`corrupt` — статус, не проходящий проверку подписей: агрегат не сходится с
подписантами, подписант не из своей группы, ключ ≠ `hash(BlockInfo)`,
`hb`/`offer_hash` не совпадают, дубль подписи.

- **Вина лидера.** Лидер — единственный, кто собирает статус; он обязан
  проверять каждую подпись до включения в агрегат.
- **Не грифинг.** Корректный лидер проверяет `sig.verify(pk, hash(blockInfo))`
  и отбрасывает плохой голос — `corrupt` у него невозможен. Злоумышленник не
  может «подставить» корректного лидера плохой подписью.
- **Доказательство:** сам статус + `leader_sig` (Ed25519 над `getHash()`).
  Все ноды независимо вычисляют `corrupt` — факт общепроверяемый.
- **Действие:** слэш лидера.

### Лидер за эквивокацию статуса

Два статуса с одним `id` и разным содержимым + две валидные `leader_sig`.

- Доказательство: обе подписи над разными `getHash()` при одинаковом `id`
  (`leader`+`id`+`rounds`+`hb` входят в хеш).
- Действие: слэш лидера.

### Что делает слэш

- `burn_all_stake` — стейк сжигается полностью (уменьшаются и `total_stake`,
  и `total_supply`).
- `staked_in` у адресов-стейкеров очищается.
- Гранула ноды **удаляется сразу** (`deleteGranule` → тумбстоун), ссылки
  (`owner`, `staked_in`) чистятся. В мете текущего раунда нода ещё есть
  (`prevStakes` — детерминированная база, `bls_pks` посчитаны до слэша),
  в кворуме текущего раунда она скипается через `slashed`, в мету следующего
  раунда уже не попадает.
- Состояние пересчитывается один раз (свёртка после слэша → корень B).

### Чего слэшем не закрыть

- **Цензура** (утаивание/фильтрация голосов лидером) — недоказуема: всегда
  «не дошло». Слэшем не закрывается и не надо пытаться. Это **liveness**, не
  safety. Митигация — ротация лидера по раундам: цензурящий лидер уходит
  следующим раундом, а голоса попадают в следующий блок.
- Решение лидера о закрытии раунда (`finished`) — законно, ноды по нему
  флушат состояние и идут дальше.

## Роли

| Кто | Что делает |
|---|---|
| Лидер | **прокси**: собирает tx (`GetTxREQ`/`GetTxRSP`), публикует офферы, складывает подписи в `agg_sig`, рассылает статус. Ставит `finished` (закрывает раунд) — это его законное решение |
| Комитет | исполняет офферы, подписывает `BlockInfo` |
| Не-комитет | применяет диффы, подписывает `BlockInfo` |
| Все | проверяют кворумы, применяют слэш, финализируют |

## Маршрутизация

| Что | Кому |
|---|---|
| `TxContainer` (оффер) | только комитету |
| `att_data` | всем (комитет перекеширует) |
| `BlockStatusREQ` | всем |

## Транспорт tх

Никаких таймаутов на «ожидание tx» нет. Всё — поток: tx приходит, кладётся
в кеш (ключ `hash(offer)`, результат — `hash(offer+"result")`), и исполняется,
если данные в кеше есть. Нет в кеше — догружается через `async_dl` у подписантов.
Субблок финализируется по закрытию окна раунда, а не по таймауту одного tx.

## Открытые вопросы

- Злоумышленник может выстрелить второй подписью **после** кворума и не быть
  слэшнутым (эквивокация ловится только до кворума).
- `outOfQuorum` — обсуждали, в итоге не нужен: поздний голос вставляется
  в `accepted`, но кворум засчитывает только победивший хеш.

## Последовательность субблоков

Субблоки исполняются **строго последовательно**: нельзя начать следующий, пока
предыдущий не зафиксирован. Состояние меняется последовательно, на основе
предыдущего. Поэтому «параллельные комитеты по субблокам» не годятся — они
ломают это требование (два субблока трогали бы одно дерево конкурентно).

Параллелизм возможен только **внутри** одного субблока (независимые tx), но не
между субблоками. Комитет и лидер — функция от `(round)`; субблок в мету не тащим.

## Производительность

Движок быстрый: HTTP-тест (js, в `mt`) на Ubuntu/M4 даёт порядка **380k RPS** —
это уже с учётом парсинга HTTP и TCP-оверхеда. Значит на простых методах
контрактов TPS упирается не в исполнение, а в агрегацию подписей и свёртку
состояния (и в последовательность субблоков).
